cpp-database-engine

A disk-backed database engine built from scratch: a head-to-head comparison of a B+-tree and an LSM-tree behind one storage interface, ARIES-style crash recovery, MVCC snapshot isolation, and a small SQL front-end with a real access-path optimizer — each claim backed by a reproducible benchmark, not just a design doc.

What's built

Architecture informed by CMU 15-445 and Hellerstein/Stonebraker/Hamilton's Architecture of a Database System — the code itself is original, not derived from BusTub.

  1. 00Disk manager, buffer pool scaffolding, CI & Docker from day one
  2. 01Buffer pool manager — LRU-K eviction, beats plain LRU on a Zipfian trace at every pool size
  3. 02Engine A: a disk-backed B+-tree — page-overlaid nodes, splits/merges, range scans
  4. 03Engine B: an LSM-tree — skip-list memtable, Bloom-filtered SSTables, size-tiered compaction
  5. 04Write-ahead log & ARIES-style crash recovery, proven with a real fork()/SIGKILL harness
  6. 05MVCC concurrency — four isolation levels, dirty read/non-repeatable read/write skew made to appear and vanish on demand
  7. 06A tiny SQL front-end — lexer, parser, and a planner that actually picks access paths
  8. 07Validation — differential testing against real SQLite, TPC-C/H-inspired workloads
  9. 08Deployment — this page, a published container image, and a read-only HTTP API

B+-tree vs. LSM-tree: no crossover in throughput, a clear one in read amplification

100,000 keys, Zipfian-skewed mixed read/write workload, swept from 5% to 90% writes.

Write %B+-tree ops/sLSM ops/sB+-tree reads/opLSM reads/op
5%541k1.19M0.1060.401
30%560k1.50M0.1060.263
50%550k1.58M0.1060.198
70%550k1.85M0.1060.119
90%530k1.97M0.1060.042
The LSM-tree wins outright on throughput at every write fraction tested — no crossover in this range. But read amplification tells the textbook story instead: the B+-tree's disk-reads-per-op is flat (~0.106, one tree descent regardless of workload); the LSM-tree's falls from 0.401 to 0.042 as writes increase, crossing the B+-tree's line around 75–85% writes. Cheap writes, workload-dependent reads — made directly measurable.

ARIES recovery: checkpoints only help if recovery can find them cheaply

Log size (ops)Recovery, no checkpointRecovery, checkpoint every 100 txns
1,0000.44 ms0.016 ms
5,0001.93 ms0.015 ms
10,0003.96 ms0.016 ms
50,00022.2 ms—
Without checkpointing, recovery time scales linearly with log size — with it, recovery stays flat regardless of log size. Getting the flat line required fixing a real bug: the first implementation replayed only the log since the last checkpoint, but still located that checkpoint with a full scan from the start, silently defeating the point of checkpointing. This benchmark caught it directly.

MVCC: fine-grained locking holds up under contention; a global lock collapses

ThreadsMVCC ops/sCoarse-lock ops/s
1375k23.8M
2572k3.20M
4554k1.39M
MVCC throughput holds roughly flat from 1 to 4 threads; a single-mutex baseline collapses ~17× over the same range. Also required a real fix: the transaction table itself was one global mutex, undermining the per-key locking beneath it — sharding it 16 ways (same technique already used for buffer-pool frames and LSM tier locks) is what produced the flat line.

The tiny SQL optimizer: picking the right access path is worth orders of magnitude

The exact same logical query, issued on an indexed column vs. an unindexed one holding identical values.

RowsPoint, indexedPoint, unindexedSlowdown
1,0001.12 µs51.7 µs46×
10,0002.13 µs869 µs408×
100,0003.86 µs14,444 µs3,742×
At 100,000 rows, choosing the right access path is a ~3,700× difference for a point query — and the gap is still widening with table size, not leveling off. The indexed path costs one B+-tree descent regardless of table size; the unindexed one is a full table scan every time. This is what the planner (src/sql/planner.cpp) exists to avoid.

A TPC-C-inspired New-Order transaction (11 of 13 statements are writes) favors the LSM-tree by ~1.4×, consistent with the head-to-head result above. A TPC-H-inspired full-table filter shows cost tracking table size, not result size: a 9× increase in matched rows costs only ~1.5× more time. (Neither claims compliance with the official TPC-C/TPC-H specs — see DESIGN.md for exactly why.)

Try it

Pull the published image

docker pull ghcr.io/kavyasridhar1501/cpp-database-engine:latest
docker run --rm -it ghcr.io/kavyasridhar1501/cpp-database-engine:latest

Or build from source

git clone https://github.com/kavyasridhar1501/cpp-database-engine.git
cd cpp-database-engine
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --parallel
ctest --test-dir build --output-on-failure

All numbers on this page are from a 4-core containerized sandbox, recorded for trend-tracking across phases — not a hardware performance claim. Reproduction commands and full context for every result are in BENCHMARKS.md.
